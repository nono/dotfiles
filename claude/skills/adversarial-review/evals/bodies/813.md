## Problem

[sc-4954](https://app.shortcut.com/template-systems/story/4954): the execution-completion manager (ECM) offered a command result on an unbuffered channel for 10 ms, then closed and deleted the entry whether the result was delivered or not. When the robot reported a later command while the plan loop still waited on an earlier one, the result was lost. The loop then found no entry for that command and stopped the whole fleet with `401 … internal channel error`, although the robot did its work.

## Change

- `ecm/ec_manager.go`: the completion channel has one slot, like the acknowledgement channel. The first signal puts the result in it, marks the entry `signalled` and keeps it. The waiter removes the entry after it reads the result. A second signal is refused with `ErrExecutionAlreadySignalled` and runs no callback. `GetAckChannelState` refuses a signalled entry, so a duplicate report is not completed twice. `ErrResultNotDelivered` can no longer occur and is removed.
- `mqtt/handlers/new_plan.go`: the loop removes a command's entry after it reads the result. The failure paths already did so through `cleanupRemainingCommandChannels`.
- Log levels: `RemoveExecution` warns about discarded callbacks only for an entry that was never signalled. The expected refusal on the sync acknowledgement path is logged at Debug.

**Behaviour change:** success callbacks (stacking notifications; pick, restock and inspection presentation; charging) run when the robot reports success, even if the loop is still on an earlier command. Before, they ran only when the loop was listening. In the case this story fixes, they did not run and the fleet stopped.

## Verification

- `TestRunSubPlans_CompletesACommandTheRobotReportedEarly` drives the real `CmdExecutedHandler`. It failed before the fix with the story's 401 stop and passes now: no stop, both commands counted `completed`, no entry left.
- `TestRunSubPlans_FailsACommandReportedBeforeItsAcknowledgementOnTheAcknowledgement`: a report that comes before its acknowledgement now fails the plan on the acknowledgement, not on a 401.
- `TestRunSubPlans_StopsTheFleetOnACommandWhoseEntryIsGone` pins the remaining missing-channel exit (the stale sweep).
- New ECM unit tests: a kept result, a refused second result, and the removal warning.
- `go test ./agents-controller/...`, `-race` on `ecm` and `mqtt/handlers`, and the plan-loop tests with `-count=20`: all pass.
- `make lint`, `make lint-prose` and `make integration-test SHARDS=agents-controller`: all pass.
- An adversarial review (4 reviewers, one of them a Quint model of the ECM and the plan loop) found no defect in the fix. On the branch, the model reaches the 401 exit only after the stale sweep; on the base, it breaks that invariant.

## Not in this PR (pre-existing, found in review)

- MQTT handlers run concurrently (`SetOrderMatters(false)`), so two copies of the same `cmd_executed` can both pass the acknowledgement check and run `completeExecution` twice.
- An acknowledgement and its `cmd_executed` that arrive together can be processed in the wrong order. The report then looks out of order, is forced to fail, and stops the fleet.
- A pick, restock or inspection callback registered after its Lift 1 already reported is accepted but never runs. The base loses it the same way.
