## Problem

[sc-5159](https://app.shortcut.com/template-systems/story/5159): the AC can publish a resume two times. When a restock operation completes normally, the MS does not record it as settled. The second copy of its resume then ends the Lifty's next restock operation:

- the Lifty waits at the module: the MS records a deposit for the next operation, which the operator did not restock, and releases the Lifty;
- the next plan still runs: the run fails with `received a resume signal but its plan is not done yet`, and the MS goes to SYSTEM_STOP.

sc-5116 fixed this only for superseded operations. The same failure also occurs when an inventory outcome resolves the operation: the one-slot `ResolvedRestockResumes` marker is consumed by the first copy.

## Change

`settleRestockOperation` is now called:

- in `handleSuccessfulRestock`, when the plan was dispatched;
- in `handleLateRestockCompletion`. The superseded path goes through it, so `settleOtherRestockOperations` no longer settles that path a second time;
- in `settleOtherRestockOperations`, when a resume consumes the `ResolvedRestockResumes` marker.

A duplicate resume that names one of these operations is then consumed.

Not covered: pick and inspection resumes name no operation, so this fix cannot catch their duplicates (a msg_id dedup in `ResumeHandler` would). Paths that delete a dispatched booking without a resume (failed signal, give-up, role flip) do not settle its operation either.
